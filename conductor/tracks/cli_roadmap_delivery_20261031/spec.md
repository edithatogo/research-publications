# Specification: CLI-first deferred roadmap

## Authority and finish line

The user requested a plan, efficient sequencing, anticipated blockers, a
one-test/one-verify cadence, and incorporation into Conductor on 31 October 2026.
**No feature implementation, acquisition, deployment, native invocation, refresh,
permission change or new automation is authorised by this track.** Execution
requires a later user selection of a bounded slice; it does not select the entire
roadmap automatically. Routine decisions within a subsequently authorised slice
should not create further approval loops.

The planning deliverable is this specification, a dependency-ordered plan with
named existing tools and measurable exits, and links from the current registry
and handoff. Planning completion does not establish any native capability.

## Protected baseline

Reuse the accepted 1,344-record publication generation, existing reader, exports,
12 retained-source packages, private receipts and qualified CLI wrappers. Keep
the two newer PubMed records deferred unless their admission is later selected.
The exporter remains monthly on day 1 at 07:00, the monitor daily at 07:45, and
the existing one-time verification on 1 November at 07:50, Australia/Brisbane.
The existing noon delivery deadline remains unchanged. Do not add a monitor or
use manual runs as scheduled proof. Close that existing occurrence independently
before promoting roadmap changes into the working publication path.

## Delivery requirements

1. Prefer existing CLI collectors, retained raw archives, typed projections,
   guarded writers, model builders and recovery tools over new frameworks.
2. Keep generation identity, complete raw payload/schema, selected key sets,
   provenance and protected human fields through each data-to-consumer slice.
3. Separate executable CLI source, operation-specific native qualification and
   accepted output. A readable model does not prove model-authoring permission.
4. Use one focused offline test invocation and one consolidated native verify
   episode per bounded implementation slice. Reuse unchanged receipts and stop
   after success. See the exact cadence in [the plan](plan.md).
5. Stop a blocked slice at its concrete missing dependency and continue only an
   independently authorised, disjoint slice. No client cycling, speculative
   callback routes, automatic mutation retries or synthetic live evidence.
6. Keep current Python 3.15.1, exact locks, Apache-2.0 notices, ordinary Git hooks,
   source ownership and private native/authentication stores intact. Do not
   replace an environment supporting an in-flight operation.

## Candidate outcomes

Retained archive consumer adoption and provenance; source-qualified publication,
dataset/software and funding relationships; identifier-based author links;
bounded DoRA activity registry qualification; selected freshness and acquisition;
evidence-based outcomes and forecasting; CLI recovery/portability. Existing
source implementations may already cover most of a slice: only its remaining
consumer connection or native acceptance is implementation work.

API-backed reader changes, multi-user features and structured documents are
conditional extensions. Visual/accessibility acceptance, cross-user privacy,
human identity decisions, sign-in/consent and substantive document approval are
not represented as fully unattended CLI-only work.

## Out of scope

No blanket implementation of historical unchecked tasks; no premium connector,
capacity purchase, new consent, email/subscription activation, public release,
shared production model overwrite, Windows/Desktop fallback, universal adapter,
new identity inference from names, or institution-wide completeness claim.
Current licensing/access limits remain actual constraints, not invitations to
substitute clients. Missing evidence remains unavailable rather than zero.
